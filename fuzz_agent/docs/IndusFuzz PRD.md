一、项目背景与缘由
1.1 工业协议的安全现状
工业控制系统（ICS）协议（如Modbus、S7Comm、IEC 61850）在设计之初几乎没有考虑安全性，只追求功能性和实时性。这导致了大量真实世界中的安全漏洞：

CVE-2026-44107：攻击者可通过Modbus TCP在无需认证的情况下触发充电控制器重启，造成拒绝服务攻击。

CVE-2026-4436：低权限远程攻击者可通过Modbus报文操纵寄存器值，导致天然气管道中加臭剂注入过多或过少。

Delta Electronics DVP12SE PLC：Modbus TCP服务无认证、无访问控制，允许未授权交互。

OpenPLC_v3：Modbus主机代码中存在堆缓冲区溢出漏洞。

1.2 传统模糊测试的痛点
依赖专家经验，耗时长

覆盖不全，难以适应私有协议

人工分析响应、判断异常效率低

无法快速生成多样化的测试用例

1.3 项目契机
学术界已验证多智能体LLM用于工业协议模糊测试的可行性（MALF框架，2026年3月发表）。但在工程界，尚无成熟的开源工具广泛流传。这是一个“学术界刚验证、工程界空白”的窗口期。同时，我的“通信工程 + AI开发”复合背景，正是这个项目最需要的。

二、项目目标
构建一个多智能体协作系统，自动对工业协议（以Modbus为主）进行模糊测试，发现潜在漏洞，并生成可复现的报告。

参考框架：MALF框架，使用Qwen2.5-14B模型，在Modbus/TCP上实现88-92%的测试用例通过率。

七、隐私风险与本地化方案

关于“DeepSeek厂商是否知道这个项目”：使用本地Ollama部署的DeepSeek模型，数据不会离开你的电脑。只有使用云端API时，数据才会发送到服务器。所以用本地模型就没问题。

十三、常见问题解答（来自开发讨论）
Q1：编写智能体，相当于编写一个AI模型吗？
不是。智能体是“编排AI模型”，它调用LLM作为大脑，但本身是程序模块，不需要训练模型。

Q2：最小闭环做完，是个软件？网页？还是终端？
建议从终端（CLI）开始，第3周加上Web界面。最终形态是Web应用。

Q3：多智能体框架的隐私安全如何保证？
全部本地部署（Ollama + AgentScope），数据不出电脑。

Q4：工业协议本身有隐私安全问题吗？
有，协议无认证、无加密。但你在本地模拟环境测试，不涉及真实设备。

Q5：开发工具（Trea、AgnesCode）会泄露项目吗？
会有风险，但可规避：只用本地AI助手，或只粘贴脱敏后的代码片段。

Q6：Qwen2.5-14B模型合适吗？
非常适合。有学术验证（MALF框架），工业术语准确率93%，你的硬件可跑。

Q7：需要下载哪些模型？总共多少G？
Qwen2.5-14B-Instruct GGUF量化版，约8-15GB。硬盘预留25GB足够。

Q8：需要准备多少API费用？
最小闭环阶段约0.06元/次测试，几乎可忽略。有$5免费额度。

Q9：这个项目在AI领域真的无人开发吗？
学术界刚有论文（2026年3月），工程界无成熟开源工具。窗口期还在。
